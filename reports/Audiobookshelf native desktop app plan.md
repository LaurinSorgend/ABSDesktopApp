# Build a lean Rust client for Audiobookshelf

Build it as a Rust workspace: a UI-free core crate (API client, SQLite cache, sync, downloads, merge layer), a Slint UI, libmpv for audio, souvlaki for MPRIS/SMTC media controls, and the ebook reader as a separate small webview process running foliate-js, with pdfium for PDF. That combination is the one the research supports for "native on Windows and Linux, no Electron, small and memory-efficient": Tauri measured close to Electron in RAM on WebView2 ([tauri#5889](https://github.com/tauri-apps/tauri/issues/5889)), Slint was the cleanest Rust toolkit on Windows accessibility and IME in a 2025 hands-on survey ([boringcactus](https://www.boringcactus.com/2025/04/13/2025-survey-of-rust-gui-libraries.html)), and libmpv is the backend that comparable server-client players already ship ([Supersonic](https://github.com/dweymouth/supersonic)). The Audiobookshelf (ABS) server makes multi-server and multi-user support simple at the protocol level, because auth is just an independent JWT access/refresh token pair per account. The hard part is the merged library: ABS item ids are per server, progress is per user per server, and no existing client merges libraries across several ABS servers or users. Treat merging as an optional, user-correctable layer on top of strictly per-account data, and ship it after the MVP. The MVP covers multiple accounts with a switcher, browsing, streaming playback with correct session sync, and OS media controls. Downloads and offline sync, the ebook reader, the merged view, and OIDC follow in that order.

## The server API is stable enough, if you treat its source as the spec

ABS has no versioned API. Behaviour changes ship in minor releases, the official API docs say they "are out-of-date and are no longer maintained" ([api.audiobookshelf.org](https://api.audiobookshelf.org/)), and the repo's OpenAPI spec covers only some controllers ([docs folder](https://github.com/advplyr/audiobookshelf/tree/master/docs)). Releases came roughly monthly through 2026, up to **v2.37.2 on 2026-10-23** ([GitHub releases](https://github.com/advplyr/audiobookshelf/releases)). The practical consequence: hand-write a small typed client for the endpoints you need, make serde models tolerant of unknown fields, read `serverVersion` from the unauthenticated `GET /status` and gate features on it ([Server.js](https://github.com/advplyr/audiobookshelf/blob/master/server/Server.js)), and run contract tests against pinned ABS Docker versions in CI.

### Auth: per-account token pairs, never hard-coded lifetimes

Since **v2.26.0** ABS uses short-lived JWT access tokens plus rotating refresh tokens ([v2.26.0](https://github.com/advplyr/audiobookshelf/releases/tag/v2.26.0)). A native client calls `POST /login` with header `x-return-tokens: true` so the refresh token comes back in the JSON body instead of only as a cookie, then refreshes with `POST /auth/refresh` and header `x-refresh-token`. On a 401 it refreshes and retries ([Auth.js](https://github.com/advplyr/audiobookshelf/blob/master/server/Auth.js); [Discussion 4460](https://github.com/advplyr/audiobookshelf/discussions/4460)). These routes sit at the server root, not under `/api`, and `ROUTER_BASE_PATH` can put the whole server under a subpath ([v2.37.2](https://github.com/advplyr/audiobookshelf/releases/tag/v2.37.2)).

The notes disagree on default lifetimes. Discussion 4460 gives the original 2.26.0 defaults of 12 h access / 7 days refresh, while the server source for 2.37.2 sets **1 hour access, 30 days refresh, and a 10-minute refresh grace period**, all overridable by environment variables ([TokenManager.js](https://github.com/advplyr/audiobookshelf/blob/master/server/auth/TokenManager.js)). The change happened in v2.31.0 ([v2.31.0](https://github.com/advplyr/audiobookshelf/releases/tag/v2.31.0)). The source reading is authoritative for current servers, but since admins can override the values and they have already changed once, the client should read the `exp` claim from each JWT and schedule refreshes from it.

Two details shape the token code. Refresh tokens rotate on every use, and v2.35.1 fixed a bug where "duplicate refresh tokens across sessions can cause unexpected logout" ([v2.35.1](https://github.com/advplyr/audiobookshelf/releases/tag/v2.35.1)), so run a single in-flight refresh per account and persist the new refresh token before discarding the old one. Since v2.36.0, refresh tokens are only accepted at `/auth/refresh` and are rejected as bearer tokens on API and websocket routes ([v2.36.0](https://github.com/advplyr/audiobookshelf/releases/tag/v2.36.0)). Mend's vulnerability database lists this fix as CVE-2026-73085 ([Mend](https://www.mend.io/vulnerability-database/CVE-2026-73085/)); the notes did not confirm the CVE number against the ABS advisory itself. Auth endpoints are rate-limited to **40 attempts per IP per 10 minutes** by default ([Discussion 4460](https://github.com/advplyr/audiobookshelf/discussions/4460)), which matters if several accounts on one server refresh at startup.

Old non-expiring tokens are still accepted in 2.37.2 but flagged ([TokenManager.js](https://github.com/advplyr/audiobookshelf/blob/master/server/auth/TokenManager.js)). Set the minimum supported server to 2.26.0 and do not build on legacy tokens. Admin-created API keys work as bearer tokens and, since v2.37.0, on websockets ([v2.37.0](https://github.com/advplyr/audiobookshelf/releases/tag/v2.37.0)); offer them as a secondary login method, which Skald also does ([Skald](https://github.com/Fireb-08/Skald)).

OIDC is possible but needs server-admin cooperation. The native flow uses PKCE S256 against `GET /auth/openid`, and the app's `redirect_uri` must be on the admin's `authOpenIDMobileRedirectURIs` list, which defaults to `audiobookshelf://oauth` ([OidcAuthStrategy.js](https://github.com/advplyr/audiobookshelf/blob/master/server/auth/OidcAuthStrategy.js)). The client has to call `/auth/openid` and `/auth/openid/callback` with the same cookie jar, or the server returns `400 No session` ([Auth.js](https://github.com/advplyr/audiobookshelf/blob/master/server/Auth.js)). The Rust TUI Absotui already does this on desktop with a loopback listener at `http://127.0.0.1:41729/callback` that the admin must whitelist ([absotui](https://github.com/pdwaldrop/absotui)). That is a proven pattern to copy, but it belongs after the MVP.

### Multiple servers and multiple users cost almost nothing on the protocol side

Every API call is a stateless bearer request, and the server stores one refresh session per login, so the same user can hold several sessions ([Discussion 4460](https://github.com/advplyr/audiobookshelf/discussions/4460)). Multiple servers and multiple users on one server are just multiple token sets. The one coupling is playback: starting a session **closes any open session for the same user and `deviceId`** ([PlaybackSessionManager.js](https://github.com/advplyr/audiobookshelf/blob/master/server/managers/PlaybackSessionManager.js)). Generate a stable `deviceId` per account, not per machine, so two of your accounts never close each other's sessions.

### Playback, progress and offline sync are already designed for clients like this

`POST /api/items/:id/play` takes `deviceInfo`, `mediaPlayer` and `supportedMimeTypes`. If every audio file's MIME type is in that list the server returns direct-play tracks, each with a `contentUrl` and `startOffset`; otherwise it starts an ffmpeg HLS transcode. A non-array `supportedMimeTypes` silently forces transcoding ([Book.js](https://github.com/advplyr/audiobookshelf/blob/master/server/models/Book.js); [PlaybackSessionManager.js](https://github.com/advplyr/audiobookshelf/blob/master/server/managers/PlaybackSessionManager.js)). The HLS output is 6-second MPEG-TS segments ([Stream.js](https://raw.githubusercontent.com/advplyr/audiobookshelf/master/server/objects/Stream.js)). With an FFmpeg-based player you declare every common audio type and get direct play nearly always.

Report progress through `POST /api/session/:id/sync` with `currentTime` and `timeListened`, and close with `/close`, rather than patching progress directly. The official docs warn that third-party apps using non-recommended endpoints cause problems such as wrong listening stats ([ABS docs: Third-Party Apps](https://www.audiobookshelf.org/docs/documentation/community/community-apps)). For offline listening, `POST /api/session/local-all` accepts a batch of locally recorded sessions and applies each one only if its `updatedAt` is newer than the server's progress, returning `{id, success, progressSynced}` per session ([PlaybackSessionManager.js](https://raw.githubusercontent.com/advplyr/audiobookshelf/master/server/managers/PlaybackSessionManager.js)). The server already implements last-write-wins, so the client needs a durable queue and a reliable clock, not its own conflict engine. Open sessions idle for **36 hours** are closed as stale.

Realtime updates come over Socket.IO: connect to the server root, emit `auth` with the access token, wait for `init` or `auth_failed`. `user_item_progress_updated` is emitted only to that user's sockets on every sync ([SocketAuthority.js](https://github.com/advplyr/audiobookshelf/blob/master/server/SocketAuthority.js)). With 1-hour tokens the socket must re-auth after each refresh; Skald uses `rust_socketio` for this ([Skald](https://github.com/Fireb-08/Skald)).

### Downloads and ebooks are plain file endpoints

`GET /api/items/:id/download` streams a zip for multi-file items, while `/api/items/:id/file/:ino/download` serves single files; both require the user's `canDownload` permission ([LibraryItemController.js](https://github.com/advplyr/audiobookshelf/blob/master/server/controllers/LibraryItemController.js)). Use per-file downloads: they map one-to-one to tracks and should support HTTP Range resume, while the streamed zip has no length and cannot resume (Range support on file routes was not verified and needs a test). Covers are served without auth at `/api/items/:id/cover` with width, height and `webp|jpeg|png` format parameters, so the client can fetch thumbnails at display size ([v2.36.1](https://github.com/advplyr/audiobookshelf/releases/tag/v2.36.1)). Ebooks (`epub, pdf, mobi, azw3, cbr, cbz`) come raw from `/api/items/:id/ebook/:fileid?` ([globals.js](https://github.com/advplyr/audiobookshelf/blob/master/server/utils/globals.js)), and reading position lives in media progress as `ebookLocation` and `ebookProgress` ([MediaProgress.js](https://github.com/advplyr/audiobookshelf/blob/master/server/models/MediaProgress.js)).

## No existing client covers this exact combination

The niche is open but not empty, and the official docs list only one Windows/Linux client ([ABS docs: Third-Party Apps](https://www.audiobookshelf.org/docs/documentation/community/community-apps)). **yaabsa** (Flutter, Vito0912) targets Windows and Linux among many platforms, has ebook/PDF support and is actively developed; its author also wrote several ABS server auth PRs ([yaabsa](https://github.com/Vito0912/yaabsa); [v2.31.0](https://github.com/advplyr/audiobookshelf/releases/tag/v2.31.0)). Its predecessor Buchable offers fast account switching across servers but lists no media notifications on Windows and very basic ebook support ([abs_flutter](https://github.com/Vito0912/abs_flutter)). **Skald** is Tauri 2 + React + Rust with LibVLC, keyring token storage and SQLite, in "working alpha", and its "All Libraries" shelf merges one server with local folders, not several servers ([Skald](https://github.com/Fireb-08/Skald)). The Rust TUIs Toutui and Absotui run on Linux and macOS only ([Toutui](https://github.com/AlbanDAVID/Toutui); [absotui](https://github.com/pdwaldrop/absotui)).

Account switching exists; **simultaneous multi-account with a merged, deduplicated library does not** in any surveyed client. Music clients with multi-server support (Supersonic, Feishin, Symfonium) switch or filter rather than merge, and Symfonium's support says cross-provider duplicate handling "is hard without proper hashes and even more when dealing with multiple providers" ([Symfonium support](https://support.symfonium.app/t/option-to-blend-off-duplicates/3362)). Merging is the feature that differentiates the app and also the one with the least prior art, which is why the plan puts it after the core works.

Before starting, decide whether contributing to yaabsa would meet your goals. It already runs on both platforms. Flutter desktop has a roughly 100 MB-class memory baseline in older measurements ([szibele.com, 2019](https://szibele.com/memory-footprint-of-gui-toolkits/)), so it fits "small and memory-efficient" less well, but it would save a year of work.

## Slint plus libmpv is the smallest stack that does everything

### GUI: Slint first, Qt 6 as the conservative alternative

The memory evidence is weak across the board. No current benchmark measures the candidates the same way, and the best numbers are old: a 2019 non-scientific measurement put Qt at 17 MB, GTK3 at 5 MB, Electron at 74.6 MB and early Flutter desktop at 98 MB of private memory ([szibele.com](https://szibele.com/memory-footprint-of-gui-toolkits/)). What is well measured is that **Tauri is not lighter than Electron at runtime on Windows**: 399 MB vs 318 MB with the same web app, and similar USS on Ubuntu ([tauri#5889](https://github.com/tauri-apps/tauri/issues/5889)). That rules out a webview-first UI for the main window, and with it the Skald approach.

Among natively drawn toolkits, Slint has the best evidence for Windows as a first-class target. In April 2025 testing with Narrator and a Japanese IME, Slint worked fully with Narrator, while iced failed both tests and GTK4 failed Narrator ([boringcactus](https://www.boringcactus.com/2025/04/13/2025-survey-of-rust-gui-libraries.html)). iced 0.14 has since added IME support but still lists no accessibility work ([iced 0.14.0](https://github.com/iced-rs/iced/releases/tag/0.14.0)). Slint is at 1.x with a release roughly every two months, from 1.14 in October 2025 to **1.18.1 in September 2026** ([Slint releases](https://github.com/slint-ui/slint/releases)). Its license is GPL-3.0, a royalty-free license that requires an About-dialog widget or download-page attribution, or commercial ([Slint terms](https://slint.dev/terms-and-conditions)). For an open-source app, GPL-3.0 avoids the attribution clause and matches libmpv and the likely app license.

Slint has gaps you will work around. It has no built-in virtualized wrapping grid, so the cover grid is a `ListView` of rows sized from the window width, and covers are decoded on a worker thread and pushed back to the event loop (these are background-knowledge patterns in the notes, not verified). It has no HTML renderer, which pushes the ebook reader out of the main window. Tray icons and file dialogs come from the `tray-icon` and `rfd` crates.

Qt 6 is the lower-risk alternative if you prefer C++ or PySide6: it has the most complete platform integration, QTextBrowser for basic HTML, Qt PDF under LGPLv3, and Qt Multimedia with FFmpeg as the default backend and pitch compensation since 6.10 ([Qt Multimedia 6.12](https://doc.qt.io/qt-6/qtmultimedia-index.html); [Qt MediaPlayer](https://doc.qt.io/qt-6/qml-qtmultimedia-mediaplayer.html)). The costs are LGPL relinking obligations ([Qt LGPL obligations](https://www.qt.io/development/open-source-lgpl-obligations)), heavier packaging, and no built-in MPRIS/SMTC. It is the right choice if the Phase 0 spike shows Slint's grid or text handling is too limited.

### Audio: libmpv, with an audio-only LGPL build on Windows

libmpv covers every codec ABS serves, HTTP with custom headers, HLS as a fallback, chapters, caching, and pitch-preserving speed. mpv auto-inserts `scaletempo2` when speed is above normal ([mpv manual](https://mpv.io/manual/master/)). Supersonic uses it for gapless playback and ships MPRIS and SMTC ([Supersonic](https://github.com/dweymouth/supersonic)), and Jellyfin Desktop uses it through MpvQt ([Flathub](https://flathub.org/sv/apps/org.jellyfin.JellyfinDesktop)). libmpv can be built **LGPLv2.1+ with `-Dgpl=false`** ([mpv build docs mirror](https://www.mintlify.com/mpv-player/mpv/embedding/building)), and an existing MinGW builder produces LGPL Windows DLLs with FFmpeg built without `--enable-gpl` and TLS through SChannel ([libmpv-mingw64-builder](https://github.com/emveepee/libmpv-mingw64-builder/wiki/License)). The Rust binding `libmpv2` 6.0.0 requires mpv 0.35+ ([docs.rs libmpv2](https://docs.rs/crate/libmpv2/latest)). On Linux, use the distro's or the Flatpak runtime's libmpv, so size only matters for the Windows installer. No measured size for an audio-only bundle was found; the notes estimate tens of MB.

The pure-Rust alternative (symphonia 0.6 + rodio 0.23 + stream-download + a time stretcher) would be smallest and permissively licensed, but symphonia marks AAC and MP4 as **not gapless**, decodes only AAC-LC natively, has no HLS or MPEG-TS support, and you would build streaming, seeking and speed control yourself ([Symphonia](https://github.com/pdeljanov/Symphonia); [docs.rs stream-download](https://docs.rs/crate/stream-download/latest)). Since M4B/AAC is the most common audiobook format, that is the wrong trade for a first version. Keep the player behind a trait so it could be swapped later. Avoid GStreamer on Windows: the official deployment guide warns that bundling the full runtime "installs unnecessary files" and requires hand-picking plugins ([GStreamer Windows deployment](https://gstreamer.freedesktop.org/documentation/deploying/windows.html)).

For OS media controls, `souvlaki` 0.8 gives one API for MPRIS and Windows SMTC; it needs the window's HWND on Windows, which winit-based Slint exposes, and has a pure-Rust zbus backend on Linux ([souvlaki](https://github.com/Sinono3/souvlaki)). A 0.9 rewrite is in progress. If it stalls, the `windows` crate's SMTC interop and `mpris-server` are direct replacements (unverified in the notes).

### Ebook reader: foliate-js in a separate process, opened only while reading

ABS's web reader uses epub.js and PATCHes `{ ebookLocation: location.start.cfi, ebookProgress: location.end.percentage }` to `/api/me/progress/{id}`; on load it only accepts saved values starting with `epubcfi` ([EpubReader.vue](https://github.com/advplyr/audiobookshelf/blob/master/client/components/readers/EpubReader.vue)). Writing valid EPUB CFIs is therefore what makes reading position round-trip with the web reader.

**foliate-js** (MIT) renders EPUB, MOBI, AZW3, FB2 and CBZ, includes an EPUB CFI parser and generator, and does not load whole books into memory ([foliate-js](https://github.com/johnfactotum/foliate-js)). It is what Foliate and Readest use. It has no formal releases and the maintainer recommends a git submodule, so pin a commit. The native alternatives are worse for this project. crengine-ng is GPLv2 C++ with its own position format, MuPDF is AGPL, and a pure-Rust route (Blitz, still beta with "many bugs and missing features") would mean writing pagination and CFI yourself ([FreshPorts crengine-ng](https://freshports.org/deskutils/crengine-ng); [MuPDF licensing](https://ghostscript.com/~robin/mupdf_explored/mupdf_exploredse159.html); [Blitz](https://github.com/DioxusLabs/blitz)).

Host foliate-js through wry (WebView2 on Windows, WebKitGTK on Linux), but not inside the Slint window. wry's `build_as_child` works on Windows and on Linux X11 only, and Wayland needs `build_gtk` with a GTK container ([wry README](https://docs.rs/crate/wry/0.56.0/source/README.md)). Mixing a GTK main loop into a winit app is the integration problem to avoid, so the recommendation (an inference from these constraints) is a small `abs-reader` helper binary using tao + wry, launched by the main app when a book is opened and exited when it closes. The main process downloads the ebook bytes, so the auth token never reaches JavaScript. The helper serves them through a custom protocol and sends `relocate` events (CFI and fraction) back over stdin/stdout; the main process writes them to ABS. The webview memory, likely 100 MB or more on WebView2, is paid only while reading, and on Windows wry's `set_memory_usage_level` can lower it while inactive ([wry 0.35.0](https://v2.tauri.app/release/wry/v0.35.0/)). WebView2 ships with Windows, so download size stays small.

For PDF, use **pdfium-render** with a prebuilt pdfium library from bblanchon/pdfium-binaries, loaded at runtime only when a PDF opens ([pdfium-render](https://github.com/ajrcarey/pdfium-render)). It can render pages natively in Slint, or you can use PDF.js inside the reader helper. CBZ is a zip of images (`zip` + `image` crates, keep a small LRU of decoded pages). Skip CBR in the first versions: the unrar source is free to use for extraction but is not an open-source license ([Wikipedia: RAR](https://en.wikipedia.org/wiki/RAR_(file_format))), which complicates distro and Flathub packaging. MOBI/AZW3 work in foliate-js for free but are low priority.

## The architecture keeps all logic out of the UI and keys everything by account

### Workspace layout

| Crate | Responsibility | Main dependencies |
|---|---|---|
| `abs-api` | Typed HTTP client, serde models, token refresh middleware, Socket.IO client, version gating | `reqwest` (rustls), `serde`, `rust_socketio` |
| `core` | Accounts, SQLite repository, sync engine, download manager, merge layer, cover cache; exposes `Command`/`Event` channels | `tokio`, `rusqlite`, `keyring-core` + store crates, `directories` |
| `player` | Player trait and libmpv implementation, chapter and track mapping, sleep timer, media controls | `libmpv2`, `souvlaki` |
| `app` | Slint UI, view models, tray | `slint`, `tray-icon`, `rfd` |
| `abs-reader` | Separate binary: foliate-js in a wry window, IPC to `app` | `tao`, `wry` |

The core builds and tests without a display. The UI sends commands and renders events, which keeps Slint replaceable if the spike fails and lets you test sync and merge logic against a Docker ABS instance.

### Data model: server, account, and an optional work layer

Model a **server** (with several URLs, for example LAN, VPN and public) separately from an **account** (server plus user, identified by a local UUID). Symfonium's users found that adding one server twice under two addresses duplicated every track ([Symfonium support](https://support.symfonium.app/t/issue-with-duplicate-tracks-and-missing-network-restriction-settings-in-version-14-0-0/13334)); multiple URLs per server avoids that. Key every cached row by `(account_id, remote_id)` and keep the raw server JSON in a column, so new server fields do not require migrations. One SQLite database with WAL, foreign keys and FTS5 for local search across accounts is enough. Covers live on disk in a size-capped LRU directory per account, never in the database.

Store only the refresh token per account in the OS secret store and keep the access token in memory. The Rust `keyring` crate is now `keyring-core` plus per-store crates (Windows native, D-Bus or zbus Secret Service, keyutils) ([docs.rs keyring](https://docs.rs/crate/keyring/latest)). Windows Credential Manager caps a blob at **2560 bytes** ([Microsoft Learn CREDENTIALW](https://learn.microsoft.com/en-us/windows/win32/api/wincred/ns-wincred-credentialw)), enough for one token per entry. Key entries by the account UUID, not URL plus username, so a changed server URL does not break lookups. On Linux systems with no Secret Service, show an explicit choice: "don't remember me", or an opt-in file with 0600 permissions. Inside Flatpak, the Secret portal is the route; oo7 implements it in Rust ([oo7](https://github.com/bilelmoussaoui/oo7)).

### The merge layer groups items into "works" without touching progress

Separate, merged and filtered views all sit on the same per-account tables. The merged view adds `work` and `work_member(work_id, account_id, item_id, match_method, confidence)` rows. Match in this order: the same item id on the same server under two users (exact, since it is the same item); equal ASIN; equal ISBN-13 after converting ISBN-10; then normalised title plus primary author with total duration within a small tolerance. ABS book metadata exposes `asin`, `isbn`, `titleIgnorePrefix`, authors, narrators, series and sequence ([Book.js](https://github.com/advplyr/audiobookshelf/blob/master/server/models/Book.js)). Never merge on title alone, because different narrators and abridged editions are different recordings. Store manual splits and merges so a re-sync does not undo them. These heuristics are the notes' own design, not taken from an existing audiobook client.

Progress always stays with one `(account, item)`. When the user plays a merged work, pick the member with the most recent progress, else a local download, else the user's preferred account, and sync only to that account. Mirroring progress to other members via `PATCH /api/me/progress` can be an opt-in setting limited to members whose durations match closely, since a timestamp does not map between editions.

### Sync, downloads, and memory budget

Sync the catalog with paginated `GET /api/libraries/:id/items?minified=1&limit=&page=` ([LibraryController.js](https://github.com/advplyr/audiobookshelf/blob/master/server/controllers/LibraryController.js)), then update from socket events. No "changed since" endpoint exists, so periodic re-fetches remain necessary. v2.36.0 added `GET /api/me/progress` and `/api/me/bookmarks` for bulk progress ([ABS releases](https://github.com/advplyr/audiobookshelf/releases)); on older servers, use the `mediaProgress` array in the login response. During online playback, sync every 10 to 30 seconds and on pause, seek and close. Offline, record a `play_local_<uuid>` session in SQLite and flush it with `/session/local-all` on reconnect. Correct outgoing `updatedAt` by each server's clock offset (from the HTTP `Date` header), since the server compares it with its own clock.

Downloads go file by file to `<root>/<account_id>/<item_id>/<ino>.<ext>` with a `manifest.json` holding the item JSON, chapters and cover. Write to `.part`, resume with `Range`, verify size, then rename. Limit concurrency to two or three files total and one per server. Saving the ABS chapter JSON avoids parsing chapters locally, including chapters that span files.

Memory is dominated by decoded covers, not the toolkit. Two hundred 300x300 RGBA covers are about 72 MB uncompressed, per the GUI notes. Request covers at about twice the tile size in WebP, decode only visible rows on a worker thread, cap the decoded-image cache by bytes (for example 64 MB), and page grid data from SQLite. Cap libmpv's demuxer cache with `demuxer-max-bytes`. Measure from Phase 0 onward, using Private Working Set on Windows and PSS on Linux.

## Ship a single-account player in weeks and defer the merge

| Phase | Scope | Exit criteria |
|---|---|---|
| 0. Spike (1-2 weeks) | Slint window with a virtualized cover grid of 500 items from a real server; libmpv playing a 30-40 h M4B and a multi-file MP3 book over HTTP with a bearer header; souvlaki on both OSes; wry reader helper opening an EPUB on Windows and on Wayland | Idle and browsing memory measured on Windows 11 and a Wayland desktop; seek latency in the long M4B acceptable; go/no-go on Slint vs Qt |
| 1. MVP | Password and API-key login; multiple accounts stored, with a switcher (data model multi-account from day one); library, series and search browsing; continue listening; streaming playback with direct play, session sync and close; chapters, speed, sleep timer, bookmarks; MPRIS/SMTC; keyring storage; Socket.IO progress updates; CI with ABS Docker integration tests; unsigned Windows zip and Linux AppImage | Listening on desktop and phone keeps progress and listening stats consistent; token refresh survives a day of idle and laptop sleep |
| 2. Offline | Per-file download manager with resume; offline playback from downloads; local session queue and `/session/local-all` flush; conflict prompt when local and server positions differ widely | A book downloaded, played offline, and synced after reconnect without losing or regressing progress |
| 3. Ebook reader | `abs-reader` helper with foliate-js; CFI and percentage progress written to ABS; light, dark and sepia themes, font size, TOC; PDF via pdfium-render; CBZ | A position set in the desktop reader opens at the same chapter in the ABS web reader, and the reverse |
| 4. Multi-account at once and merge | All accounts active simultaneously (one socket and refresh loop each); separate, filtered and merged views; work layer with match cascade and manual split/merge; preferred account per work | Two servers with overlapping books show one entry per work, with no wrong merges on a test library containing different editions |
| 5. Distribution and SSO | OIDC with loopback redirect; signed Windows installer with auto-update; winget; Flathub; .deb/AUR | Installs and updates cleanly through each channel without two updaters fighting |

Two choices in the table are deliberate. Multi-account storage is in the MVP because retrofitting `account_id` into every table and token path later is expensive, while showing one account at a time keeps the UI simple. Packaging starts as plain artifacts in Phase 1 and becomes signed installers in Phase 5, because signing and store submission take time but are not needed to use the app yourself.

For Phase 5, Velopack (MIT, Rust) provides installers and delta updates hosted on GitHub Releases ([Velopack](https://github.com/velopack/velopack)), and cargo-packager produces NSIS, MSI, .deb, AppImage and PKGBUILD outputs ([cargo-packager](https://github.com/crabnebula-dev/cargo-packager)). Disable in-app updates for package-manager installs. For Windows signing, Microsoft says Azure Artifact Signing (about $9.99/month) is open to individual developers only in the USA and Canada ([Microsoft Learn](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/code-signing-options)). As an individual in the EU, SignPath Foundation's free OSS signing is the realistic route; it requires builds from a public repository in CI ([signpath.org](https://signpath.org/)). Flathub's requirements page, as fetched for the notes, requires building from source with vendored crates and no network, a validated AppStream file, and disclosure of AI-generated material, and says manifests may not contain AI-generated or AI-assisted content ([Flathub requirements](https://docs.flathub.org/docs/for-app-authors/requirements)). Re-read that policy before submitting, and if you use AI tools, write the Flatpak manifest by hand.

## Risks and open questions

The biggest technical risk is **server churn**. ABS changed token lifetimes, refresh semantics, and several endpoint behaviours within a year (for example v2.36.1 stopped `PATCH /api/items/:id/media` from accepting chapters, and series and playlist endpoints are deprecated in favour of library-scoped ones) ([v2.36.1](https://github.com/advplyr/audiobookshelf/releases/tag/v2.36.1); [SeriesController.js](https://github.com/advplyr/audiobookshelf/blob/master/server/controllers/SeriesController.js)). Mitigate by testing against the oldest supported version and the latest release in CI, gating on `serverVersion`, and reading release notes for "API:" lines. When the legacy token path will be removed is unknown.

The **memory goal is unproven** for every candidate. The toolkit figures in the notes are old or unsourced, and no client publishes measurements. Phase 0 exists to measure this before committing. If Slint's grid, text input or accessibility falls short, Qt 6 with libmpv (via MpvQt) and QTextBrowser or QtWebEngine is the fallback, at higher package size.

**Linux webview integration** for the reader is the most fragile piece: wry on Wayland requires GTK, and WebKitGTK versions vary by distro. The separate-process design limits the damage, but test it on GNOME and KDE Wayland early. Inside Flatpak, the GNOME runtime provides WebKitGTK.

**Dependency maintenance** is concentrated in a few single-maintainer projects: souvlaki (mid-rewrite), libmpv2, foliate-js (no releases), rust_socketio. Keep each behind a small internal trait so it can be replaced.

**Progress conflicts** remain a product question. ABS's last-write-wins picks the latest write, not the furthest position, so offline desktop listening plus phone listening can move a user backwards. A prompt when positions differ by more than a few minutes is the proposed mitigation; how aggressive to make it is untested.

Open questions the notes could not settle: whether ABS file download routes support HTTP Range (test against a server); what the web client writes to `ebookLocation` for PDF and comics (read `PdfReader.vue` and `ComicReader.vue` before Phase 3); whether `/api/session/:id/sync` returns 404 after a server restart and how to recover (sessions are in memory); whether yaabsa already supports simultaneous multi-account or OIDC; and which license to pick. GPL-3.0 fits Slint's free option and libmpv; AGPL would also allow MuPDF if foliate-js proves insufficient.

## Conclusion

The research changes where the difficulty lies. Native playback, token handling and offline sync are mostly solved problems with clear patterns from the ABS server code, Skald and the Rust TUIs. The real design decisions are the account-keyed data model, which must be right from the first commit, and the merge layer, which has no prior art and should be built only once per-account data is reliable. The "no Electron" requirement also rules out Tauri in practice, since its runtime memory on Windows is comparable to Electron's. That pushes the one web-dependent feature, the EPUB reader, into a separate process that exists only while a book is open.

A small, careful plan follows from that: a two-week spike to measure memory and validate Slint and the Wayland reader, an MVP that is a good single-user player on a multi-account foundation, then offline, ebooks and merging. If the spike shows Slint cannot meet the UI needs, switching to Qt changes the `app` crate and the player binding, but not the core, which is where most of the work is.
